1. **Honest sitemap `lastmod` per URL** (2026-11-27, goal: impressions, effort: S) — give each sitemap URL the date its content last really changed (from git history or a stored date), instead of the build date, so Google can use `lastmod` to schedule recrawls of new and edited pages. Owner note:
   - Why here: `scripts/generate-sitemap.mjs` sets `lastmod` for every peak and best-peaks URL to the modification time of `src/data/peaks.json` (the checkout or build time on a fresh build), and to today's date for the home, compare and permit URLs. So all 312 sitemap URLs carry the same recent date after every build, whether or not the page changed. Each week adds or edits pages (new peaks, new descriptions), and Search Console shows impressions on 185 page rows over the last 28 days (2026-10-21 to 2026-11-17), against 312 sitemap URLs. Average position is 35.2 this week, so getting new and edited pages recrawled sooner is a lever that does not depend on rankings first.
   - Trend: this is search hygiene, not a product trend. Google says it uses `lastmod` only if it is "consistently and verifiably" accurate, and that it uses it to schedule crawls of URLs it already knows about ([Google Search Central, build a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap); [Google Search Central blog, 2023](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping)). A Google analyst has said the signal is binary: Google either trusts a site's `lastmod` or ignores it ([Search Engine Journal, 2024](https://www.searchenginejournal.com/googles-gary-illyes-lastmod-signal-is-binary/519239/); secondary report).
   - Build: in `scripts/generate-sitemap.mjs`, compute a per-peak date. Options in order of effort: (a) read the last commit date that touched each peak's record (for example by comparing a stored per-peak content hash in a small generated file such as `src/data/lastmod.json`, written by the build and committed), or (b) add an optional `updatedOn` field to peak records that the weekly scripts set. Permit URLs use the existing `verifiedOn` date in `src/data/permits.json`; compare URLs use `comparisons.json` `asOf`. Leave `lastmod` out for the home page and index pages whose date cannot be known. The sitemap script and its tests are the only files touched; no URLs or slugs change.
   - Risks: a wrong date is worse than none, because Google stops trusting the field. Do not bump `lastmod` for changes that are not significant (sitemap or footer edits). Vercel builds from a fresh clone, so file modification times cannot be used; the hash file or stored date has to live in the repo.
   - Measure: Search Console, Sitemaps report and Crawl stats (time from a peak being added to its first impression), and the number of peak pages with impressions, after 4–6 weeks. This needs no new analytics event.

3. **Seasonal snow-line layer on the 3D terrain** (2026-11-27, goal: engagement, effort: L) — a month slider on each peak's 3D view that shades typical snow cover for that month from an open satellite climatology, so a reader can see why "best time" is what it is. Owner note:
   - Why here: this is the use of the 3D terrain that a static photo cannot match, aimed at the "best time" half of trip intent (trip searches are 10.7% of intent, 39 of 365). Month wording is already in the data: `best places to hike in april in the world` landed on `/best-peaks/april` at position 9. Map searches are 37.3% of intent (136 of 365) and land on a 3D view with no next step. Mobile has a CTR of 3.9% (103 impressions, position 10.4) against 1.1% on desktop (562 impressions, position 39.9), so the layer must stay light on phones.
   - Trend: PeakVisor launched a Snow Report with snow maps, snow depth and a one-minute audio briefing on 19 November 2026 ([PeakVisor, Snow Report](https://peakvisor.com/en/news/snow-report.html)); AllTrails added a Fall Foliage Map layer with an eight-week forecast ([AllTrails on Reddit, 25 Sep 2026](https://www.reddit.com/r/alltrails/comments/1wq2nba/summer_highlights_from_alltrails/)). Both show seasonal map layers as a reason to open the app.
   - Build: a build-time script that samples a monthly snow-cover climatology (for example NASA MODIS or VIIRS monthly snow cover, which needs a licence and citation check before use) around each peak into a small per-peak JSON of 12 snow-fraction values by elevation band; a client-only control beside `src/components/PeakTripPanel.tsx` that tints the existing terrain by the selected month; `src/lib/seasonMonths.ts` to highlight the sourced `bestSeason` months next to the slider. Start with 10 well-known peaks. No new URLs.
   - Risks: accuracy (a climatology is not today's snow, so label it "typical, not a forecast"); cost and licence of the data source; file size and mobile performance (lazy-load the layer, cap each peak's JSON at a few kilobytes); a layer that disagrees with the page's sourced `bestSeason` would look wrong, so show both together.
   - Measure: Vercel Analytics events `snow_layer_opened` and `snow_layer_month_changed` per peak, plus pages per visit for sessions that used it, after 4 weeks. Search Console cannot measure this.
